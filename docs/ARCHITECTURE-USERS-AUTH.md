# Users, Auth, Roles & Access

* **Auth:** Supabase Auth via a cookie; no Bearer-token path. The web app (`scriptr.uk`) and API (`api.scriptr.uk`) are same-site: the API sets `sb-auth-token` with `Domain=${COOKIE_DOMAIN}` (`.scriptr.uk`), `SameSite=Lax`, `Secure`, `httpOnly`, so the browser and Server Components (which forward it explicitly, `getRequestCookieHeader`) both receive it. `COOKIE_DOMAIN` is unset locally (`localhost` ports share cookies). `*.vercel.app` preview deployments are cross-site and won't receive the cookie. Access tokens are configured for the maximum one-week lifetime to reduce refreshes (`hono/supabase/config.toml`; hosted Supabase projects must use the same Auth setting). Routes: register, login, logout, session, and `/auth/callback`, which the frontend (`useAuthCallback`) calls with tokens extracted from the email-confirmation URL fragment (implicit flow, no PKCE). `/login`, `/callback`, and `/session` return the same app-shaped session user (id, email, username, role, subjects, selected faculty/study ids), so the client doesn't refetch the session after login. `/session` refreshes tokens only when they expire within 60 seconds; protected client actions that receive a 401 refresh the session and retry once, then sign out and notify the user if authentication still fails. A DB trigger creates the profile on signup.
* **Onboarding:** on first visit users select university/faculty/study/subject; selections persist to the `profile_*` tables. Onboarding and account creation each generate a notification. The selection cascade and year/subject completion logic (`useAcademicSelections`) is shared by the onboarding wizard (guest localStorage) and the profile's "Edit academics" dialog (local state seeded from the account); copy lives in `UI_STRINGS.onboarding`.
* **Roles:** `profiles.role` is `student`, `moderator`, or `admin`. Only `admin` carries elevated privilege (full CRUD on scripts/comments/profiles, flag resolution, rating types, restrictions, and the v1 moderation UI). The admin layout returns 404 for non-admin sessions and the nav entry is hidden; API authorization and RLS remain the boundary. `moderator` has no elevated access.
* **Guests:** can browse, preview, and download. Upload, like, comment, save, rate, and flag require auth.
* **Restrictions:** `profile_restrictions` has one row per user and is active while `expires_at` is `null` or later than now; existing null rows remain permanent. `is_restricted()` ignores expired rows. Each application is recorded in `profile_restriction_history`; ladder count is history not lifted early: 14 days, one calendar month, then permanent. Reapplying to an active restriction updates only its reason. Lifting an active restriction marks its latest history row `lifted_early_at`; removing an expired row does not affect the ladder. Restricted users are blocked from creating/updating scripts, comments, flags, comment reactions/likes, votes, and ratings, but can still delete their own content. Favorites are exempt.
* **Profile selections:** `profile_id = auth.uid()` RLS tables. `PATCH /profiles/me` replaces faculty/study selections (diffed, errors checked; admins editing another user use the service-role client since the tables have no admin RLS path); subject selection carries a status (`completed` | `currently_taking`) and is written per subject. Stored `currently_taking` rows are not relied on for display (registration writes them, the onboarding sync and academics editor don't): profile pages derive "currently taking" as the non-completed subjects of the selected studies.
* **Profile pages:** `ProfilePage` is the one layout for `/user` (client `MyProfilePage` over the shared profile state, editable) and `/user/[username]` (server-fetched; redirects to `/user` for the viewer's own username). Favorites and subjects are public: `script_favorites` is publicly readable and the public profile endpoint returns subjects. Academic links are built from Sanity slugs via the onboarding catalog (`buildProfileAcademics`), not Postgres ids.
* **Avatars:** `profiles.avatar_url` is a full public URL, not an R2 key, because it is used directly as an image `src` on cached pages (comments, script cards, the header, the profile page) and a signed URL there would expire inside the cache. An upload is two calls, mirroring a script file upload: `POST /profiles/me/avatar/upload-url` presigns a PUT into `staging/{userId}/`, the browser sends the photo straight to R2, and `POST /profiles/me/avatar` runs it through the optimizer's avatar profile (EXIF-oriented, cropped square around the most interesting region at 320 px, metadata stripped, WebP at ≤200 KB, aiming for 100 KB; limits in `shared/config/avatar.ts`). The result is stored in the **same bucket as script files**, at `avatars/{userId}.webp` — one key per user, overwritten on every change — and the profile stores `${R2_PUBLIC_URL}/avatars/{userId}.webp?v={version}`. The `?v=` is what makes that safe: the key never changes, so each upload needs a new URL for browser and CDN caches, and R2 ignores the query when resolving the object. Account deletion removes the one key. Serving avatars this way means the bucket needs a public domain, so script objects become readable by key (they stay random UUIDs and are only handed out with a script); the URL is rendered with `next/image`'s `unoptimized` so the image optimizer's per-image quota isn't spent on it, which also removes the `remotePatterns` host allow-list as a backstop — so the column grant is the real boundary: `avatar_url` is written only with the service-role client, and `authenticated` has no `INSERT`/`UPDATE` grant on it. Without `R2_PUBLIC_URL`, avatar uploads answer `503` rather than storing an uncropped photo.
* **Preferences:** `profile_preferences` is an own-row RLS table, separate from publicly readable `profiles`. Its versioned v1 shape controls optional toast delivery and achievement notifications; missing rows use defaults. Restriction and moderation notices are never user-configurable.
* **Achievements:** `achievement_definitions` (entity type — only `profile` — metric, threshold, `rarity`; new achievements are a data insert) plus `profile_achievements` (one row per profile per achievement). `rarity` is one of five ordered tiers (`common`, `uncommon`, `rare`, `epic`, `legendary`; `ACHIEVEMENT_RARITIES` in `shared/config/achievements.ts`, mirrored by a DB CHECK). An award-check helper runs on vote, download, and comment mutations. The seeded catalogue gives every metric one achievement per rarity tier — four metrics × five tiers, twenty definitions — with thresholds climbing inside each metric and a distinct icon per achievement in `ACHIEVEMENT_ICON_OVERRIDES`. Title and description live in code (`ACHIEVEMENT_COPY` in `shared/config/achievements.ts`, resolved with `getAchievementCopy`), so a wording change is a reviewable commit that updates badges, the admin list and the notification together; metric, threshold and rarity stay as data because the award helper and the admin editor read them. An id with no catalogue entry cannot be created: `POST /achievement-definitions` rejects it, so an admin adding an achievement starts by adding its wording to the catalogue. The row keeps a copy of that text purely as a snapshot for anything that reads the table directly. Awards are permanent: nothing recomputes or revokes them, and deleting scripts never removes one (an admin can still delete a row through the RLS DELETE policy; there is no endpoint). Definitions apply retroactively only on a user's next qualifying mutation of that metric — a new or lowered definition awards on the next action, with no backfill. Hiding achievement notifications never suppresses awards.
* **Achievement badges:** every profile payload (`/me`, `/:id`, `/username/:username`, and the list) embeds each earned achievement with its definition (title, description, metric, threshold, rarity). `ProfileCard` takes a `badges` slot, so it stays unaware of achievements; `ProfilePage` fills it with `AchievementBadges`, ordered by `sortAchievements` (rarest first, then newest). Colour comes from the rarity (`ACHIEVEMENT_RARITY_PALETTES`) and the icon from the metric, with per-achievement overrides (`next/lib/achievement-display.ts`). Badges sit below the avatar from `lg` and beside it below `lg`. `/user` re-fetches `/me` once on mount because the shared profile state otherwise loads once per session.
* **Notifications:** `notifications` (`profile_id`, `type`, `title`, `body`, `data jsonb`, `is_read`). `type` is unconstrained so new kinds need no migration. Users can list (filter by read state), count unread, mark one/all read, and delete their own. Kinds include onboarding, account creation, achievements, restrictions applied/lifted, content removed by an admin, and admin alerts when five distinct reporters flag the same target. The tray merges server rows with per-user local notifications, sorts unread first, caps its list, and refetches on mount and tray open, the tray refetch throttled to once per 15 s and the API limiting each user to 15 notification requests per minute (no polling, realtime or focus refetch); the restriction notice and preferences are cached in local storage (`next/lib/account-state-storage.ts`), read from the API once on login, rewritten on save, refetched only when a cached restriction lapses or a newer restriction notification appears, and cleared on logout (`/restrictions/me` and `/profiles/me/preferences` are limited to 15 requests per minute per user). A non-dismissible restriction notice comes from `GET /restrictions/me`, so deleting notification rows cannot hide it. While it is shown, the dismissible `restriction_applied` row is hidden from the tray so the notice is the single, non-dismissible copy.
* **Ratings:** professors and subjects are rated on extensible types via `rating_types` (public read, admin write). One rating per user per type per entity, score 1–5, a trigger rejects target mismatches; restricted users can't create/change, removal stays allowed. On the frontend, `RatingsSection` renders inside the professor About card and the subject details card, loading criteria, stats and the viewer's own scores in the browser (the pages stay static); the viewer's restriction comes from `GET /restrictions/me`, with a 403 on save as the fallback.
