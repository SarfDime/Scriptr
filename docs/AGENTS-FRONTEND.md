# Frontend (`next/`) — Next.js 16, React 19

The root [Global Rules](../AGENTS.md#global-rules) still apply. Architecture: [Frontend Structure & UI Conventions](ARCHITECTURE-FRONTEND.md) and [API Client & Response Typing](ARCHITECTURE-API-CLIENT.md).

* Server Components by default; add `'use client'` only for real interactivity/state/effects and `'use server'` only for real Server Actions. No speculative directives.
* React Compiler is on (`reactCompiler: true`) — don't hand-write `useMemo`/`useCallback`/`React.memo`; justify any exception in a comment.
* `params`/`searchParams` are `Promise`s in pages, layouts and `generateMetadata` — always `await`. This is a hard failure in 16, not a warning as in 15.
* Turbopack is the default bundler; no webpack-specific config without a documented reason.
* There is no middleware today. If request interception is needed, add `proxy.ts` (Node.js runtime) — never `middleware.ts`.
* `revalidateTag()` needs a `cacheLife` profile (a bare single-argument call behaves differently now); scripts revalidate by tag on mutation ([`ARCHITECTURE-SCRIPTS-UPLOADS.md`](ARCHITECTURE-SCRIPTS-UPLOADS.md)). `/api/revalidate` keeps `revalidateTag(tag, { expire: 0 })` so a mutation never serves stale data.
* **Static routes are pinned:** a route that is build-time only declares `export const dynamic = 'force-static'` and `export const revalidate = false` next to (or above) `generateStaticParams` / the page export — see `app/sitemap/[section]/route.ts`, `app/sitemap.xml/route.ts`, `app/[locale]/(app)/auth/page.tsx` and the five academic detail pages. Never add them to a route that reads `searchParams`, `cookies()` or `headers()` (`/`, `/search`, `/user`, `/admin/*`, a study's `/calendar`), and remove them if such a read is added later: `force-static` makes those APIs return empty values instead of failing, so the mistake shows up as missing data, not an error. Client components (`'use client'`) cannot carry segment config.
* **No time-based revalidation:** cached API reads (`cachedPublicRead`/`cachedUnlessPersonalized`) and Sanity reads (`fetchSanityData`) pass `revalidate: false`, so an entry changes only on a rebuild or a tag invalidation. A Hono mutation that changes a cached read must call `revalidateCacheTags` with tags from `shared/config/cache-tags.ts` — an untagged read never refreshes on its own.
* `next/image`: assume 16-era defaults (async decoding, `fetchPriority: auto`, `qualities`/`minimumCacheTTL`/`imageSizes` in `next.config.ts`) — not the 15 behaviour.
* UI: follow [`next/STYLING_GUIDE.md`](../next/STYLING_GUIDE.md) exactly — reuse `Box`/`Card`/`Button`/`Badge`/`Divider` and the `ui-*`/`cp-*` classes; never invent a class absent from `styles/`. Theme through `next/providers/theme/`, never hardcoded colours. Add a utility only at 3+ repeats, and update the guide.
* **New env var → startup checklist:** add it to `ENV_REQUIREMENTS` in `next/lib/startup-report.ts` (reported by `instrumentation.ts` on server start). `NEXT_PUBLIC_*` values are inlined at build, so the entry should say so.
* **API calls:** only `apiFetch` (`next/lib/api/next-api.ts`) and the per-domain wrappers in `next/lib/api/*-api.ts`, with paths from `apiRoutes` (`shared/config/api-routes.ts`) — never a new `fetch` pattern or a hardcoded path string.
* **`SITEMAP_SECRET` and `/api/sitemap/*` are server-only — a hard rule:**
  * Never give `SITEMAP_SECRET` (or any service-to-service secret) a `NEXT_PUBLIC_` prefix, never add it to `env` in `next.config.ts`, and never log it, return it from a Server Action or route, or pass it to a Client Component.
  * Never call the sitemap route from a user's browser: no Client Component, hook, `'use client'` module or Server Action may send `x-sitemap-secret` or use `apiRoutes.sitemap.*`.
  * The only call lives in `next/lib/api/sitemap-api.ts`, which starts with `import 'server-only'` so a client import fails the build, and is read only from `lib/sitemap-entries.ts` (served by `app/sitemap/[section]/route.ts`). Don't read the secret from `config/env.ts`, which client code imports.
  * It is the last shared-secret route in `next/`. If a feature seems to need another, make it a session-authenticated route in `hono/` instead, or ask first.
  * Before shipping a change near this: after `corepack pnpm build:next`, grep `next/.next/static` for `x-sitemap-secret` and for the real secret value; both must return nothing.
* **Admin actions are gated twice:** an admin session *and* a twenty-minute TOTP unlock. `app/[locale]/(app)/admin/layout.tsx` checks the session and the unlock and shows `AdminAccessGate` (a code form) instead of the page when it is missing or spent. Every admin page **also** calls `requireAdminUnlock` (`next/lib/admin-page-guard.ts`) before its loader: a layout is not re-rendered on a client-side navigation between admin pages, so an unlock that lapses while the tab is open would otherwise let the page render and its loaders answer `401`. Start every admin page with `const cookie = await requireAdminUnlock(); if (!cookie) return <AdminAccessGate />` and pass that cookie to the loader. Loaders pass the incoming cookie through to the API and inherit the HttpOnly `scriptr-admin-access` cookie with it; the client-side 401 path refreshes, which re-renders the gate. Keep admin pages under `/admin` (the gate is the layout) and never read the token in a component.
* Every screen needs loading, error and empty states, and semantic/ARIA-correct HTML.
* **Fields own their label and description wiring:** `Field` generates the ids, and a control inside it takes them from `useFieldControl` (`components/ui/field/field-context.ts`) — `InputWrapper`, `TextArea`, `Select` and the Portable Text editor already do. Don't hand-roll `id`/`aria-describedby` for a field; pass `grouped` when the children are several controls or composed content (a dropzone, a list of links), so the label names the group instead of pointing at one control.
* **Toast severity:** `error` and `warning` toasts go to the assertive `role='alert'` region, everything else to the polite one — pick by what the toast reports (`components/ui/toast/ToastContainer.tsx`). A failure interrupts; a success waits its turn.
* **Localization keeps the component split.** A translated entry is `{ en, mk }` inside its own collection (`shared/strings/*`, `UI_STRINGS`), and a collection's `_PACK` export is the source of truth; the historical export is its English view, so un-migrated imports keep working (mechanism and limits: [Frontend Structure & UI Conventions](ARCHITECTURE-FRONTEND.md#frontend-structure--ui-conventions)).
  * A **Client Component** reads copy with `useUIStrings()`/`useStrings(pack)` (`providers/locale/use-strings.ts`). Any table or label array built from strings must move inside the render — module-scope copy freezes the first language. A file that calls one of these hooks **is** a Client Component and has to say so with `'use client'`: without the directive a Server Component that imports it renders it on the server, where the hook throws at request time — the build passes, so the mistake surfaces as a 500 (`AcademicBadge`, `InputWrapper` and `OnboardingSubjectsStep` were each missing it).
  * A **Server Component** awaits `getServerStrings(<AREA>_PACK)` (`next/lib/server-strings.ts`) and renders the string directly. One exception is worth knowing: `PageHeader`'s `greeting`/`title`/`subtitle` take a `LocalizedMessage` (a string *or* an `{ en, mk }` entry) and resolve the entry themselves, so a page whose header is all the copy it needs passes the raw entry (`CALENDAR_STRINGS_PACK.pageTitle`) and reads no collection at all. It resolves them with `useLocale()` and is therefore a Client Component itself: `PageLayout` renders it and `ProfilePage` imports `PageLayout`, so this module lands in the client bundle, where `next/root-params` exports nothing — the `getServerLocale()` version of it fails the build, whatever the caller. `SearchResults` is the worked example: every message and group label resolved once at the top of the component, which therefore stays out of the client bundle (`SearchForm` and `LanguageToggle` are what its page hydrates). Never read a collection at module scope in a server file either — that freezes the default language.
  * Copy that has to be a **string** in a **Client Component** — an attribute, or a prop typed `string` — comes from `useCopy('path')`; `SimpleModeToggle` sets its `title` that way. Import the path types (`UIPath`, `CalendarPath`, `StringPackPath<P>`) from `@shared/config/string-packs` rather than re-deriving `StringPath<typeof …>` in each file.
  * **Every address the app mints carries the locale.** `localizedPath(path, locale)` (`shared/utils/localized-path.ts`) is the one rule — unchanged for `en`, `/mk`-prefixed otherwise, absolute study URLs included — and the builders (`getAcademicPath`, `getStudyFeedPath`, `getStudySiteUrl`, `catalogUrl`, `studyUrlFromPath`) take a `LocaleId`. Get it with `await getServerLocale()` in server code and `useLocale()` in client code. A literal `href` is an address too: a link that stays in the app is built, never written as `/start`. A component rendered from a Client Component must use the hook, which is why `ScriptCard`, `SubjectCard`, `ProfileCard`'s page and `NavLogo` are `'use client'`.
  * **The remembered language is a cookie.** `setStoredLocale` writes `scriptr-language` to `localStorage` and to a plain (`SameSite=Lax`, non-`HttpOnly`) cookie, because the `next.config.ts` redirect that sends `/` to the reader's language can read only a cookie. It is a preference, never authorisation — don't derive permissions from it.
  * **Sanity text comes back in the reader's language.** Every projection in `next/sanity/queries/` reads a localized field through `localizedProjection(alias, source)` (or `localizedValue` for a `match` filter and an `order()` clause) from `next/sanity/queries/localized.queries.ts`, so the query keeps the field name it always had and components never see a `localized*` object. The localized object is the only source: the legacy single-language fields were deleted in Phase 9, so a projection never falls back to one. Two constraints to keep: the helper must stay an expression-bodied arrow over a plain template string, and the languages must be read by name (`x.en`), never by index (`x[$locale]`) — `sanity typegen` statically evaluates the query, silently drops what it cannot, and types a computed key as the whole object. A read that renders passes `locale: await getServerLocale()` to `fetchSanityData`; a read with no reader (`generateStaticParams`, a route handler) omits it and gets the default language.
  * **Dates come from `shared/utils/date-format.utils.ts`, never from `Intl` or `toLocaleDateString`** for month and weekday names. A runtime without a language's data does not fail: `mk-MK` resolves to `en-US` in a browser built without Macedonian, which rendered an English date inside a Macedonian page and disagreed with the server (Node ships the data), so hydration replaced the right text with the wrong one. The names live in `shared/strings/date-strings.ts`; pass `'utc'` for calendar day keys and the default `'local'` for a "now". Relative times go through `formatDate` (`TIME_AGO_STRINGS_PACK`), whose Macedonian forms use `mkCount` for the counted singular (21 минута, 5 минути).
  * **The locale is a route param:** the page tree lives under `app/[locale]`, which is the root layout and owns `<html lang>`; route handlers (`app/api/*`, both sitemap trees) stay outside it. **A page reads it from its own `params`** — `LocalePageProps<T>` / `LocaleRouteParams` (`next/types/localization.types.ts`), which types the segment as a `LocaleId` — and hands it to `getServerStrings(pack, locale)`; anything below a page (a component, a `next/lib` helper) leaves that argument out and reads the route param instead (`getServerLocale()`, `next/lib/server-strings.ts`, wraps `next/root-params`). Two things it cannot do: a **layout** must declare `locale: string` (Next's generated `LayoutConfig` rejects a narrowed type — the root layout narrows it itself and is what makes the page's `LocaleId` true), and a **route handler or `generateStaticParams`** has no route locale at all, so `getServerLocale()` answers the default language there. `generateStaticParams` stays on the `[locale]` layout, or every page under it silently goes dynamic. The layout validates the segment against `LOCALES` — `[locale]` matches any first segment, so without that an unknown one renders a page.
  * **Verify a localization change per language, not per build.** The build only proves it compiles. Check `lang` in the HTML source, the page title, the canonical, one `aria-label`, one sitemap entry carrying both alternates, a document authored in only one language, and a client-side navigation between the two locales with no full reload. After a build, `next/.next/server/app/[locale]/…/page_client-reference-manifest.js` is the quickest way to see whether a component actually crossed into the client bundle.
  * Never import `next/providers/locale/*` from `shared/`, `hono/` or `sanity/` — those read the collections directly (English) or call `getStrings(pack, locale)`. `global-error.tsx` stays at `app/` in English (it replaces the root layout); `not-found.tsx` and `error.tsx` live under `[locale]`, and both `metadata` and their copy read the route's language. `next/lib/server-strings.ts` starts with `import 'server-only'`, so a Client Component importing it fails the build — and a route handler has no route locale at all: `next/root-params` is App-Router-render-only and `getServerLocale()` falls back to the default language there instead of throwing (a route handler reads slugs, not copy). Metadata that renders still reads it from a render, which is why `createAcademicMetadata` lives in `next/lib/academic-metadata.ts`, apart from the helpers the sitemap handlers import.
  * **Macedonian copy is short and natural, not literal.** Macedonian words run longer than English ones, and a control sized for "Light" breaks on "Светла". Translate the meaning, then cut it down: prefer the shorter noun to the adjective, drop filler, and avoid chained "на" phrases. The theme options are `Ден` / `Ауто` / `Ноќ`, not `Светла` / `Автоматска` / `Темна`; a legend is `Тема`, not `Тема на бои`. When a translation is much longer than the English, shorten the copy before changing the layout — and check the widest control it lands in (a segmented toggle, a nav label) with the Macedonian string, not the English one.
* **Icon-only controls still need a name.** `AccessibleNameProps` forces one for a button or link with no children, but it cannot see that `<Button><CloseIcon /></Button>` has none: an element is children too. Give a `<Button>`/`<NextLink>` whose only child is an element an explicit `aria-label`, and treat a scan for that shape as a review item, not something the compiler catches.
* **Keep pages thin:** a new or refactored `page.tsx` awaits params, calls a loader in `next/lib/<feature>-page.ts` (fetching, cookies, 404s) and composes components that take a view model from `next/types/components/`. Components don't fetch; one responsibility each. See [`ARCHITECTURE-FRONTEND.md`](ARCHITECTURE-FRONTEND.md).
